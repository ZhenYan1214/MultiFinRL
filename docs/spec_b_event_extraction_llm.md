# Spec：事件抽取改成 LLM-based

狀態：規劃完成，尚未實作（來源：2026-08 grill-me 討論，接續 `docs/decisions.md` #32/#33 的關鍵字方法結果）

## Problem Statement

事件抽取目前用關鍵字規則判斷某一天是不是發生了七類重大事件之一（財報、併購、新品發表、訴訟、財測、股利、高層異動）。修正過公司相關性判斷與沿用舊資料誤判的問題後，對照 149 天的人工標記 ground truth，precision 只有 0.162（recall 0.868、f1 0.273）——recall 不錯，代表原始資料裡真的有把事件記下來，但 precision 低，代表關鍵字規則會誤判出大量不是真的發生的事件。關鍵字比對本身是規則式的粗略判斷，沒有真正理解文字內容，這個 precision 的天花板很可能就是這個方法本身的極限，繼續調整關鍵字清單邊際效益有限。

## Solution

把事件抽取的判斷邏輯，從關鍵字規則改成呼叫大型語言模型（LLM），讓模型直接讀當天的新聞、財報、法說會文字內容，依照跟 ground truth 標記時同一份判斷標準，輸出當天發生的事件類型。先在既有的 149 天 ground truth 樣本上跑一次，直接算出新的 precision/recall/f1，用小成本驗證這個方法真的比關鍵字規則好，再決定要不要擴大到全部 1381 天。舊的關鍵字方法保留、不刪除，作為免費、可隨時比較的對照組。呼叫的 LLM 服務商設計成可切換，先用 DeepSeek 做初期測試，之後也能換成 GPT（OpenAI）或 Claude，不綁死單一供應商。

## User Stories / Scenarios

1. 作為專案負責人，我想知道把事件抽取換成 LLM-based 之後，precision 是不是真的比關鍵字規則高，這樣才知道這個改動值不值得。

2. 作為專案負責人，我想先用少量樣本（149 天）驗證效果，再決定要不要花全額成本（1381 天）跑全量，這樣不會在方法還沒驗證前就花大錢。

3. 作為專案負責人，我想讓 LLM 抽取跟 ground truth 標記用同一套判斷標準（同一份事件定義、同一種「一天一次判斷」的粒度），這樣兩者的比較才公平、算出來的 precision/recall/f1 才有意義。

4. 作為專案負責人，我想保留原本的關鍵字方法，這樣任何時候都能免費跑一次當基準線，比較兩種方法的差異，也不會浪費之前已經調校過的成果。

5. 作為專案負責人，我想要能自由切換要呼叫哪一家 LLM 服務商（DeepSeek、OpenAI、Claude），這樣之後不管是為了省錢、比較品質、或供應商政策變動，都能直接換掉而不用重寫程式。

6. 作為專案負責人，我想先用 DeepSeek 做初期測試（成本較低），但架構要留好切換空間，之後打算換成 GPT 的 API，這樣現在做的設定不會白做。

7. 作為執行者，我想在送出每一天的內容給 LLM 之前，先用便宜、機械式的公司相關性檢查濾掉明顯不相關的新聞，這樣可以在不影響判斷品質的前提下減少花費的字數（進而減少費用）。

8. 作為執行者，我想要抽取過程能中斷續跑：已經處理過的日期不會重複呼叫 LLM、重複花錢，這樣就算執行途中斷線、出錯，也不用整批重新開始、重新付費。

9. 作為執行者，我想清楚知道這支程式要在哪裡執行——因為呼叫 DeepSeek 需要能連到 DeepSeek 的伺服器，而目前用來輔助開發的沙盒環境連不到 DeepSeek（實測會失敗），只能連到 Claude 的伺服器，所以這支程式需要在本機、有正常網路的環境下執行。

10. 作為專案負責人，我想知道 API key 是我自己加進環境設定檔，不透過對話內容傳遞，這樣金鑰不會被記錄在不必要的地方。

11. 作為之後接手或參與的團隊成員，我想知道「一天一次呼叫、整合當天所有來源」這個設計選擇背後的取捨——會失去「這個事件是哪一篇新聞、哪一段財報觸發的」這種來源追蹤細節，換取跟 ground truth 標記粒度一致、成本可控，這樣理解這支程式的行為時不會誤以為它遺漏了功能。

## Decisions

- 先在既有的 149 天 ground truth 樣本上執行 LLM-based 抽取，直接對照計算新的 precision/recall/f1，驗證效果優於關鍵字方法後，再決定是否擴大到全部 1381 天。

- 若確認效果，全量執行時延續同一套服務商設定（DeepSeek），不臨時切換；未來若要比較不同服務商的品質差異，透過既有的可切換設計隨時執行即可，不需要重新設計。

- LLM 服務商設計為可切換（至少支援 DeepSeek、OpenAI、Claude 三種），供應商與對應的預設模型分開設定，方便之後切換到 GPT 的 API，不用改動核心邏輯。

- 每一天只呼叫一次 LLM，把當天的新聞、財報片段、法說會片段整合進同一次請求，讓模型輸出當天的事件類型清單。這個粒度跟建立 ground truth 時的標記方式一致，是兩者可以直接比較的前提；代價是失去「哪一篇來源觸發哪個事件」的細節追蹤，這個細節對「有沒有發生事件」這個驗證目的不是必要的。

- 送進 LLM 之前，先用既有的公司相關性檢查（比對新聞標題是否出現公司名稱或代號）過濾掉明顯不相關的新聞，不送進 LLM 判斷。這一步純粹是為了減少送給 LLM 的文字量、降低花費，不是為了提升準確率（準確率的判斷交給 LLM 本身，prompt 裡已經有公司相關性的判斷規則）。財報與法說會片段的相關性由其本質保證（本來就是這家公司自己發布的資料），不需要這層過濾。

- 舊的關鍵字方法完整保留，不刪除，跟 LLM-based 方法並存，可透過參數切換使用哪一種方法，作為免費、可隨時重跑的比較基準。

- 抽取過程要能中斷續跑：每處理完一天就把結果存檔，重新執行時跳過已經有結果的日期，避免中途中斷或出錯時需要整批重跑、重複付費。

- 實際執行（尤其是呼叫 DeepSeek）在使用者本機進行，不在協助開發用的沙盒環境執行——已實測確認沙盒環境的網路可以連到 Claude 的伺服器，但連不到 DeepSeek 的伺服器。

- API 金鑰由使用者自行寫入本機的環境設定檔，不透過對話內容傳遞或顯示。

## Open Questions / Out of Scope

- 149 天測試若效果不如預期（precision 沒有明顯優於關鍵字方法），下一步怎麼調整（換模型、調整 prompt、還是放棄這個方向），這裡不預先決定，留到實測結果出來後再議。

- 全量 1381 天執行的實際時間長度、是否需要控制呼叫速率（rate limit），這裡不預先規劃，留到 149 天測試時一併觀察再決定全量執行的方式。

- 除了本次討論到的 AAPL，未來擴充到其他股票代號時，公司名稱對照表需要補齊，這是既有的已知限制，這次改動不處理。

- OpenAI（GPT）與 Claude 這兩個服務商的實際切換與測試，這一輪只確保架構上留好切換空間，不在這一輪實際執行或比較。

## Further Notes

這個改動是接續「事件抽取關鍵字方法的 precision 偏低」這個已知結果而來的（`docs/decisions.md` #32），也是回應「事件抽取原本在自製分工文件裡，設計意圖是要輔助驗證 Z_fused」這個架構缺口（`docs/decisions.md` #33）的其中一步——先把抽取方法本身的準確率提升到堪用的水準，抽取出來的事件才有資格被拿去做後續更進一步的驗證或比對。

事件驗證頭（`docs/decisions.md` #34）是另一條獨立驗證 Z_fused 的路徑，直接對照同一份 ground truth，不依賴事件抽取的結果，兩者是互補、分開的驗證方式，這次改動不影響事件驗證頭的既有實作與結果。
