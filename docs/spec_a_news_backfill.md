# Spec：A 新聞資料歷史回補

狀態：已結案，FNSPID 路徑不採用（來源：2026-08 grill-me 討論；結論見下方「驗證結果」）

## Problem Statement

A 目前抓新聞的方式（`fetch_news.py`，基於 yfinance）只能拿到近期新聞，沒有辦法回補到專案要求的完整時間範圍（5 年，約 2021 年至今）。原本設想用 FNSPID 這個現成資料集直接補齊歷史缺口，但實測發現 FNSPID 在 HuggingFace 上公開的整合版 CSV，Article（新聞全文）欄位在抽樣檢查的資料裡是空的，只有標題跟連結，無法直接拿來用。

FNSPID 專案本身另外附了一組抓取腳本（headline scraper + news content scraper，皆為 Selenium 網頁自動化），理論上可以自己針對指定股票重新爬一次。但這組腳本原本設計是給全市場（a-z 全部股票清單）用的，也還沒驗證過對單一股票、5 年這個時間深度到底抓不抓得到，也沒有機制把爬出來的資料轉成本專案的資料格式。

## Solution

先用這組 FNSPID 附帶的爬蟲腳本，鎖定 AAPL 單一股票做驗證測試，分兩階段進行：第一階段只抓標題與日期，確認實際能回溯到多久以前；範圍確認足夠後，才進第二階段抓新聞全文。全部驗證通過後，另外寫一支轉換腳本，把爬蟲輸出轉成本專案既有的每日新聞 JSON 格式，銜接進現有的資料建置流程。

## User Stories / Scenarios

1. 作為團隊成員，我希望知道 FNSPID 的爬蟲對 AAPL 這支股票，實際能回溯到多久以前的新聞，這樣才知道 5 年的目標範圍能不能達成。

2. 作為團隊成員，我希望爬蟲不要浪費時間去抓超過我們實際需要的年份（例如翻到 2015 年），這樣測試才不會跑太久。

3. 作為團隊成員，我希望先確認「抓得到日期跟標題」這件事，再花時間去處理「抓全文」這個更花時間、成功率更沒把握的階段，避免在還不確定範圍夠不夠的情況下，先投入心力在細節優化上。

4. 作為團隊成員，我希望爬蟲抓到的資料能自動變成 `build_dataset.py` 讀得懂的格式，而不是停留在爬蟲自己的輸出格式裡，變成一份沒有真的被使用到的資料。

5. 作為團隊成員，我希望這個第三方爬蟲工具的程式碼（連同它自己的版本控制紀錄）不會跟本專案的版本控制混在一起，造成困惑。

6. 作為團隊成員，我希望即使這次新增了新的新聞資料來源，既有「抓最新近期新聞」的機制仍然正常運作，不會被取代或破壞。

## Decisions

**測試對象與範圍**：先以 AAPL 單一股票驗證，若可行則視為對其他美股同樣適用（不逐一重新驗證）。目標時間範圍暫定 5 年（約 2021 年至今），未來視情況可能延伸到 10 年，但本輪只驗證 5 年這個目標。不預先規劃「回溯不到目標年份時」的因應方案，先實測拿到真實數字後再決定。

**分階段執行**：先執行標題階段（抓日期、標題、連結），確認回溯深度是否達標。確認達標後，才執行內文階段（抓新聞全文）。若標題階段就發現回溯不到目標範圍，內文階段暫緩，先回頭討論資料來源問題本身。

**範圍控制機制**：標題階段的爬取邏輯要新增「一旦抓到的日期早於目標起始年份，就停止繼續翻頁」的判斷，避免爬超過實際需要的範圍。

**內文階段成功率**：先前用既有範例資料驗證過，內文抓取的成功率偏低（約 16%）。這一輪先接受此一限制，能抓到多少算多少，不在本輪投入心力提升成功率；是否之後另外處理，留待之後視情況決定。

**資料格式銜接**：爬蟲兩階段完成後，需要一支新的轉換腳本，把爬蟲自己的輸出格式，轉換成本專案既有的「每日新聞 JSON」格式（沿用資料格式契約文件中新聞欄位的既有規則，包含盤後新聞歸屬邏輯），使其能被既有的資料彙整流程讀取使用。

**既有腳本的去留**：先前針對 HuggingFace 整合版 CSV 寫的轉換邏輯（獨立一支腳本），由於該資料來源的可用性存疑（新聞全文欄位目前看起來是空的），這次先擱置不使用；不會現在就刪除，等新的轉換腳本驗證可行之後，再視情況決定是否移除。負責抓「近期最新新聞」的既有腳本（yfinance 版）維持不變，跟這次的歷史回補是互補關係，不是取代關係。

**版本控制**：從第三方 clone 下來的工具原始碼，因為自帶獨立的版本控制紀錄，已排除在本專案的版本控制追蹤範圍之外，避免巢狀衝突；程式檔案本身仍留在專案資料夾內，路徑不變。

## Open Questions / Out of Scope

- 若標題階段測出回溯深度不足 5 年，後續要用什麼方式補缺口（例如另尋資料來源、調整範圍目標、或跟老師重新確認 5 年這個要求的彈性）——本輪不預先決定，留待實測結果出來後再討論。
- 內文抓取成功率偏低的根本原因與改善方式——本輪不處理，列為後續可能的優化項目。
- HuggingFace 上另一份未驗證過的整合版檔案，其新聞全文欄位是否真的有內容——本輪不會另外驗證，先前擱置的轉換腳本去留待日後一併重新評估。
- 這次驗證只鎖定 AAPL，之後若要擴充到其他股票，是否會遇到不同的回溯深度限制或抓取成功率差異——本輪不驗證，留待實際擴充時再確認。

## Further Notes

爬蟲執行本身需要真的開啟瀏覽器（Selenium + 對應版本的瀏覽器驅動），且需要連線到外部網站即時抓取，這部分只能在有完整網路存取權限的環境下實際執行與驗證，沒辦法在沒有對外連線能力的環境裡先行測試或預測結果。

## 驗證結果（2026-08，結案）

票 1 實際在本機執行後，發現的問題比原本預期的「翻頁範圍夠不夠」更根本，卡在更前面一步：

1. **自動化瀏覽器被網站阻擋**：Selenium 執行時卡在「Loaded Logo → Time out or wrong url」無限重試迴圈，desired_page 永遠停在 0。追查後發現是腳本本身每次重試都會清空瀏覽器 cookies（`driver.delete_all_cookies()`），導致 nasdaq.com 的 cookie 同意視窗每次都重新跳出擋住頁面；加上「等待點掉 cookie 視窗」的修補後，問題仍未解決——改用 Claude in Chrome（另一種自動化操作的瀏覽器）連到同一網址，一樣卡在新聞列表載入骨架、抓不到任何真實內容。但同一網址用一般手動瀏覽器開啟，內容正常顯示。兩種自動化瀏覽器都遇到一樣的狀況、手動瀏覽器沒事，判斷是 nasdaq.com 對自動化流量做偵測、刻意不提供真實內容。
2. **頁面結構已改版**：直接查驗目前頁面的 DOM，發現 scraper 寫死要找的新聞項目 class（`quote-news-headlines__item`）、當前頁碼 class（`pagination__page--active`）都已經不存在於現在的頁面上，網站前端應該是重新設計過。就算解決了第 1 點的偵測阻擋，抓取邏輯本身也已經過時，需要整段重寫。
3. **現成 dataset 重新驗證，全文欄位確認為空**：透過 HuggingFace dataset-server API 重新抽樣（100 筆），`Article` 欄位全部是 null；連 dataset 本身附的四種自動摘要欄位（Lsa/Luhn/Textrank/Lexrank_summary）也全部是 null——代表這些列本來就沒有全文可用於生成摘要，不是抽樣運氣不好。另一份未驗證過的 `All_external.csv` 因下載受限無法直接檢查，但屬於同一個 dataset，沒有跡象顯示會不同。

**結論**：FNSPID 的爬蟲工具與現成 dataset 兩條路都不可行，新聞歷史回補（2021~2023 缺口）需要另尋資料來源或方法，本輪就此結案。決策記錄見 `docs/decisions.md` #26。

## 後續（2026-08）：改用 Alpaca News API，已成功

改用官方新聞 API（Alpaca News API，來源 Benzinga）取代 FNSPID，本機實測 AAPL
2021-01-01~2026-08-08：15,989 則、1,459 天、總耗時約 10 分鐘，內容抽樣檢查皆為
真實全文。程式碼：`module_a_data/crawler/fetch_news_alpaca.py`。決策記錄見
`docs/decisions.md` #27。原本保留供參考的 FNSPID 相關程式碼（`FNSPID/` 目錄、
`fetch_news_fnspid.py`、`fetch_news_local_scrape.py`）已實際刪除，`requirements.txt`
移除 selenium。這份文件（含上方「驗證結果」段落）保留作為決策過程紀錄，不代表目前
程式碼庫裡還有對應檔案。
